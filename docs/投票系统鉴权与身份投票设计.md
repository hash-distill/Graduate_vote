# 研究生支教团投票系统 —— 鉴权与身份投票详细设计

> 版本：v0.5（实施中）
> 背景：系统为内网专用（校园网/局域网），评委在各自设备上投票，管理员 1–2 人。
> 目标：在不改动现有平票/重投计票算法（`UserServiceImpl.vote()` 主体逻辑）的前提下，
> 补齐「管理员接口鉴权」与「按投票设备限一票」，并给状态落库留出路径。

> 实施状态（v0.5）：
> - ✅ Step1 管理员口令登录（application.yml 中 `app.admin.password`，默认 `2026`）
>   + 拦截器注册锁死 /admin/**（仅放行 /admin/login 与 CORS 预检）
> - ✅ Step2v2 改为「按投票设备限一票」：评委零门槛（无链接/口令/编号），
>   每台设备首次打开自动取得 deviceId（localStorage），同设备同轮只能投一次；
>   剩余名额由已投设备数推导；计票/重投判定不变。
> - ✅ Step3 只读 /vote/status 接口；waiting/show/usershow 轮询切换；重投轮 roundNo 自动续牌
> - ✅ Step4 记录型落库（vote_session / vote_log，设备维度唯一键防重）；
>   写库失败自动降级（仅告警，不影响内存状态机与计票结果）——保证与改造前计票一致。
>   ⚠️ 当前为“记录型落库”（审计/重启后留痕），状态机仍以内存为准；如需完整“重启恢复现场”
>   （读库重建 revote/last/pre），需将 vote() 数据通路迁移到 DB，属后续大项（见 §6 阶段二）。
> - ✅ 候选人额可配置：/set 支持正选人数与候补人数（默认 45 / 4）；
>   `getPreRevote` 泛化为支持任意候补名额的平票/重投判定。
> 设计取舍：无身份体系下“按设备限票”能防同设备重复/双击/多标签；
>   清缓存或无痕开新窗口可获得新设备号，现场需管理员监督（有身份需求的正式评选可改用
>   编号+口令方案，见 §5 备选）。
>
> 附加修正：审查 H5 —— /admin/setMsg 增加 limit==students 一致性校验（防计票死锁）。

## 1. 要解决的问题（对应现状）

| # | 现状问题 | 位置 | 后果 |
|---|---|---|---|
| P1 | `/admin/*` 匿名可达，无任何鉴权 | `AdminController.java` 全部接口 + `AuthenticationInterceptor` 未注册（全工程无 `WebMvcConfigurer`） | 任何人可重置参数、清票、灌候选人、触发计票 |
| P2 | `/vote` 不知道“谁在投” | `UserController.vote()` 只收 `List<Integer>` id | 无法判断评委是否已投、无法做幂等 |
| P3 | 无幂等、无已投记录 | 同上；`teachers` 手工递减 | 重复提交 → 票数翻倍 / `teachers` 变负数 → 整场死锁 |
| P4 | 状态全在 `ServletContext` 内存、共享对象原位修改 | `UserServiceImpl.vote()` 系列 | 重启/异常即丢，无法恢复 |
| P5 | 前端无“已投/结束”护栏 | 各页面 | 刷新/后退可再投、可误投假名单 |

> 设计原则：**只加固外围，不动核心算法**。`vote()` 里平票判定/正选-候补状态机经审查在常规场景自洽，
> 本轮不重构它；我们给它接上“可信输入 + 可审计记账 + 可恢复状态”。

## 2. 总体架构

```
                ┌──────────────────── 内网 ────────────────────┐
  管理员(1-2人)  │                                             │
  /login ──────▶│  AdminController (/admin/**)                │
  口令+会话Cookie│      ▲ 拦截器校验：会话有效?                  │
                │      └── AuthenticationInterceptor(真正注册)  │
                │                                             │
  评委(线下收令牌)│  /vote?ticket=XXXX  ──▶ /users(验票)        │
  一次性链接     │                            │               │
                │                            ▼               │
                │  /vote  POST {ids} + ticket ──▶ 校验：      │
                │    ①ticket有效 ②本轮未投 ③名单/上限 ④记账     │
                └─────────────────────────────────────────────┘
```

角色与信任边界：

- **管理员**：唯一的“管理面”。能设参数、导候选人、看原始结果。
- **评委**：只有“投票面”。持一次性 ticket，只能投自己该投的轮次。
- 两条面在 Spring 层用拦截器 + 请求携带凭证区分，前端路由与后端接口同步隔离。

## 3. 数据模型设计

### 3.1 评审场次与轮次（解决 P4 的状态定义问题）

现有状态全部散落在 `ServletContext` 的十余个 attribute（`limit/teachers/students/last/pre/revote/…`）与 `Map` 里。
为让“身份 + 轮次 + 幂等”有落点，引入**场次 ID** 概念，将现有状态归并：

```
VoteSession（一场完整评选 = 一次 /admin/setMsg 初始化）
├── sessionId        // UUID，setMsg 时生成
├── status           // INIT / FIRST_VOTING / REVOTE / FINISHED
├── roundNo          // 当前“投票轮次号”：
│                    //   第1轮 = 1；进入正选重投后 = 2；
│                    //   再进候补重投（或连续重投）= 3、4……
│                    //   ← 由现有 revoteTimes/preRevoteTimes 推导，见 §5
└── (现有字段全部挂到 session 下，内存版先照旧，落库版再搬表)
```

### 3.2 评委令牌表（解决 P2）

```
VoterTicket
├── ticketId     // 主键（DB 自增 / 内存 UUID）
├── voterNo      // 评委序号 1..teachers_all（管理员 setMsg 时确定总数）
├── ticket       // 随机令牌：至少 32 位（内网也避免可枚举），URL-safe
├── status       // ACTIVE（本轮可投）/ VOTED（本轮已投）/ REVOTING（重投轮已开放）
└── votedRoundNo // 该评委已投票的最高轮次号（幂等判断关键）
```

- 生成时机：管理员 `/admin/setMsg` 成功后按 `teachers_all` 生成 N 张，返回给管理员页面展示/复制。
- 分发方式：线下（微信群/打印），每人一条 `http://内网IP:8081/vote?ticket=XXXX`。
- 存活：内存版存 ServletContext；正式版存 DB 表（见 §6）。

### 3.3 投票流水表（解决 P3 幂等 + 可审计 + 落库）

```
VoteLog
├── id
├── sessionId      // 场次
├── roundNo        // 轮次
├── voterNo        // 评委编号
├── candidateId    // 候选人 vote_id
└── UNIQUE KEY (sessionId, roundNo, voterNo, candidateId)   ← 数据库级防重复
```

- 语义：评委 v 在第 r 轮投了候选人 c，恰好一行。**同轮同人同候选人只能有一行**。
- 计票 = `SELECT candidateId, COUNT(*) FROM VoteLog WHERE roundNo=? GROUP BY candidateId`，
  与现有内存计票结果天然一致（现在也是一人一票一候选人）。

## 4. 管理员鉴权设计（解决 P1）

### 4.1 登录

- 新增页面/接口：`POST /admin/login`，body `{ password }`。
- 口令存储：**不存明文**。配置项或环境变量里的口令先做加盐哈希（如 BCrypt）后比对；
  内网场景允许退化为「配置明文口令 + 恒定时间比较」，但注释标明不建议。
- 成功 → 生成 `adminSessionId`（UUID），存服务端（管理员仅 1–2 人，内存 Map 即可），
  通过 **HttpOnly + SameSite=Lax** Cookie 下发；前端不可读，防 XSS 窃取。

### 4.2 拦截（把死代码用起来）

新增 `WebConfig implements WebMvcConfigurer`（目前全工程缺失，这是拦截器从未生效的根因），注册：
`AuthenticationInterceptor` 真正实现校验，规则：

| 路径 | 规则 |
|---|---|
| `/admin/login` | 放行（登录入口本身） |
| `/admin/**`（其余全部） | 校验 Cookie 中的会话 → 无效返回 401 JSON |
| `/users` `/vote` `/hello` | 放行，但 `/vote` 走「评委票校验」（§5） |

- 401 响应体沿用 `ResultDto(false, "未登录或会话已过期", null)`，前端统一跳 `/login`。
- `/admin/getVoteResult` 目前被评委页面轮询——改造后评委页面应改轮询**只读**接口
  （见 §7 前端改动），把“触发计票”收敛为管理员动作或服务端自动触发，避免评委轮询带副作用的管理接口。

### 4.3 登出与会话

- `POST /admin/logout`：销毁服务端会话。
- 会话超时：默认 4 小时无操作失效（可配置）；管理员重开 `/set` 前重新登录。

## 5. 评委身份 + 一人一轮一次投票设计（解决 P2/P3/P5）

### 5.1 轮次号的定义与推导

为不改算法，轮次号从现有状态**推导**而非新增维护：

```
roundNo = 1 + revoteTimes(preRevoteTimes 归并前的正选重投次数) 初步方案：
更稳妥：在 setMsg 增加显式字段 session.roundNo，
进入任意重投（现有 map.put("isRevote",1) 分支）时 roundNo++，
所有“需要重投”出口（UserServiceImpl.vote() 内 6 处 put isRevote=1）统一推进一次。
```

> 实现提示：与其在每个分支手动 ++（易漏，现有代码同模式漏改过），
> 不如在 `AdminController.getVotesNum` 的同步块内、调用 `userService.vote()` **返回后**统一判定：
> 若结果 `isRevote==1` 且与上一状态不同 → `roundNo++`。单点递增，杜绝分支分叉。

### 5.2 评委投票完整时序

```
评委                 后端
 │ 打开 /vote?ticket=T
 ├──────────────────▶ GET /users?ticket=T
 │                   ①ticket 存在且 ACTIVE？
 │                   ②当前 session.roundNo 是否 == T.votedRoundNo？
 │                     相等 → 返回 {alreadyVoted:true}（防刷新再投）
 │                     小   → 正常返回学生名单 + 该评委 voterNo + 本轮 limit
 │◀────────────────── 名单(与现有一致) + voterNo
 │ 勾选、点提交
 ├──────────────────▶ POST /vote  { ids:[...] }  + ticket（Header 或参数）
 │                   ①ticket 有效、ACTIVE
 │                   ②votedRoundNo != roundNo（未投过本轮）
 │                   ③ids：去重后数量 == 本轮 limit；且均在“本轮可投名单”内
 │                   ④写入 VoteLog（唯一索引兜底；冲突即“已投过”）
 │                   ⑤标记 ticket.status=VOTED、votedRoundNo=roundNo
 │                   ⑥teachers 原子递减：UPDATE … SET n=n-1 WHERE n>0
 │                     或改为：剩余 = teachers_all - 本轮已投 ticket 数（推荐，天然无负数）
 │◀────────────────── {result:true, msg:"投票成功", voterNo}
 │ navigate(/waiting)
```

### 5.3 进入重投时“续牌”

现有流程：全部评委投完 → `teachers==0` → 计票 → 若有平票 → `isRevote=1` → 评委从 `/waiting` 跳回 `/vote`。

改造后，在“计票完成、确定需要重投”的同一出口：

```
for each ticket:
    if ticket.status == VOTED:
        ticket.votedRoundNo 保持（防旧轮重复）
    ticket.status = REVOTING     // 表示“新一轮已对你开放”
roundNo++
```

- 评委回到 `/vote?ticket=T` → `GET /users` 发现 `votedRoundNo(旧) < roundNo(新)` → 视为可投 → 正常给名单。
- 同一评委在**旧轮**再点提交 → `votedRoundNo == 旧roundNo`，但旧轮已关闭 → 拒绝（返回“本轮已结束”）。
- 同一评委在**新轮**双击 → ①请求成功写完 VoteLog；②请求撞唯一索引 → 返回“您本轮已投过”，**不重复加票、不重复扣名额**。

### 5.4 边界与异常

| 场景 | 行为 |
|---|---|
| 评委重投轮没跳回 /vote，卡在 /waiting | 与现状一致：等待页轮询到 `isRevote==1 && teachersNum==0` 时提示“等待管理员开放下一轮”，轮询继续 |
| ticket 已被使用且轮次未变 | 拒绝并提示“您已投过本轮的票” |
| 管理员中途 setMsg 重置 | 旧 session 作废、全部 ticket 失效、生成新一轮 N 张；旧 VoteLog 保留在另一 sessionId 下（审计） |
| 服务重启 | 内存版：需管理员 setMsg 重开（与现状相同但明确提示）；落库版：按 sessionId 恢复 |
| 评委数 > 实际到会 | 管理员可重发/停用未用 ticket；剩余名额判定改为“已投数==应到数时触发”的配置项（当前是 teachers_all，保持默认） |

## 6. 状态落库路径（正式版，解决 P4）

- 阶段一（内网 MVP，改动最小）：ticket/VoteLog 放内存（`ConcurrentHashMap` + `ServletContext`），
  幂等靠“单锁 + 已投集合”保证；重启需 setMsg 重开（现状即如此）。
- 阶段二（正式落库）：新增 3 张表 `vote_session / voter_ticket / vote_log`；
  计票函数改为读 `vote_log` 聚合；`session` 状态机每步写库。
  核心算法 `vote()` 输入输出不变，仅数据源替换，便于回归。
- 迁移说明：现有 `vote01` 只存候选人档案（姓名/学院/票数字段 vote_poll 仅第一轮使用），
  与 `vote_log` 并存；最终 `vote_poll` 改为计票结果冗余列或废弃。

## 7. 前端配合改动清单

| 页面 | 改动 |
|---|---|
| `/set` | 提交前校验登录态；成功后展示生成的 N 条投票链接（复制/导出），支持停用单个 ticket |
| `/login`（新增） | 管理员口令输入；失败显示后端 msg；成功回 `/set` 或 `/show` |
| `/vote` | 读取 URL `?ticket=`；无 ticket 提示“请使用管理员发放的投票链接”；显示“评委 N/M”；提交后若返回“已投过”提示而非跳走；提供“我已完成”去 /waiting |
| `/waiting` | 轮询改只读状态接口；区分“等待下一轮开放”与“已结束”两种文案 |
| `/show` `/usershow` | 轮询改只读接口（原 `/admin/getVoteResult` 拆分：读结果 → `/vote/result` 只读；触发计票 → 管理员动作或后端自动） |
| 通用 | 401 统一跳 `/login`；axios 拦截器统一读 `result` 与 `msg` |

## 9. 实施顺序（每步可独立交付、可回退）

1. **Step 1（纯增量，推荐先做）**：注册 `WebMvcConfigurer` + 让 `AuthenticationInterceptor` 真正校验；
   `/admin/login` 口令会话；除 `login` 外 `/admin/**` 全部锁死。
   —— 此步不触碰任何投票/计票代码，立即消除 P1。
2. **Step 2**：`/users`、`/vote` 增加 ticket 校验与已投集合（内存版）；`teachers` 改为由已投数推导；加“0<ids≤limit、名单内、无重复”校验。
   —— 消除 P2/P3/P5 的主要风险。
3. **Step 3**：新增只读轮询接口 `/vote/status`，前端 `/waiting`、`/show`、`/usershow` 切换过去；
   管理端计票触发与查看分离。
4. **Step 4**：落库（3 张表）+ 重投轮次自动续牌 + 重启恢复。
5. **Step 5**：回归测试矩阵（见 §10）。

## 10. 回归测试建议

| 用例 | 预期 |
|---|---|
| 无 Cookie 访问 /admin/setMsg | 401 |
| 错口令 / 对口令登录 | 拒绝 / 放行并下发 Cookie |
| 同一评委第一轮投两次 | 第二次“已投过”，票数、名额不变 |
| 双击“确定”按钮 | 只记一次（VoteLog 唯一索引兜底） |
| 平票进入重投 → 评委重投一次 | 计入新轮次；旧轮数据不可再改 |
| 重投时部分评委未投 | 轮询提示等待，不死锁（应到数按已投推导） |
| setMsg 后旧链接访问 | 提示场次已重置 |
| 重启后端（内存版） | 明确提示需管理员重新初始化 |
| 现有计票正确性 | 与改造前同一批数据结果一致（回归） |
